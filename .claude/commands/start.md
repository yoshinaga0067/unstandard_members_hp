このコマンドが呼ばれたら、以下を **この順序で** 実行してください。途中で問題があれば日本語でユーザーに伝えてください。

## ステップ0：リポジトリの確認（最初に必ず行う）

### 0.1 Git 初期化チェック

ルートに `.git/` ディレクトリが存在しない場合（ZIP ダウンロード等で取得されたケース）：
- `git init -b main` を実行
- ユーザーに一言：「ローカル用の Git を初期化しました。」

### 0.2 フェーズ判定

`.claude/phase3.lock` が存在するか確認：
- 存在しない → **フェーズ1**
- 存在する → **フェーズ3**

### 0.3 リモートの確認

`git remote get-url origin` の結果で分岐する。

**ケースA：リモートが設定されていない**

- **フェーズ1の場合** → そのまま続行する。一言だけ伝える：
  ```
  💡 GitHub にはまだ紐付けていません。ローカルで自由に作業を進められます。
     設定したくなったら「GitHub に紐付けて」と教えてください。
     ※ /publish のときに必要になります（公開だけしたい場合は Vercel への直接デプロイも可能です）
  ```

- **フェーズ3の場合** → 中断する。エンジニアに相談するよう案内：
  ```
  ⚠️ GitHub のリモートが設定されていません。
     フェーズ3 ではエンジニアが用意したリモートが必要です。
     エンジニアに相談してください。
  ```

**ケースB：リモートURLに `claude-md-template` が含まれている**

テンプレートのリモートを指したままなので、ユーザーに選択肢を提示：
```
⚠️ このフォルダはテンプレートのリモートを指したままです。
   どちらにしますか？

   A. 今すぐご自身の GitHub リポジトリを作って紐付ける
   B. テンプレートのリモートを外して、ローカルだけで進める（後で設定できます）
```

- **A を選んだ場合**：
  ```
  GitHub の手順：
  1. github.com にログインする
  2. 右上の「+」→「New repository」
  3. リポジトリ名を入力して「Create repository」
  4. 作成後の URL（例：https://github.com/yourname/projectname）を教えてください
  ```
  URL を受け取ったら `git remote set-url origin <URL>` で置き換える。

- **B を選んだ場合**：
  - `git remote remove origin` でテンプレートのリモートを外す
  - 「テンプレートのリモートを外しました。ローカルだけで進めます。」と伝える
  - 続行（以降はケースAのフェーズ1の流れと同じ）

**ケースC：別のリポジトリを指している**

問題なし。次のステップへ進む。

## GitHub を後から紐付ける場合

ユーザーが「GitHub に紐付けて」「GitHub を設定して」等と言った場合の手順：

1. リモートが既にあるか `git remote get-url origin` で確認
   - 既に別の URL が設定されていれば「すでに紐付け済みです」と伝える
2. ユーザーに URL を聞く：
   ```
   GitHub のリポジトリ URL を教えてください。
   まだ作っていない場合：github.com/new で新しく作成できます。
   ```
3. URL を受け取ったら：
   - `.git/` が無ければ `git init -b main`
   - `git remote add origin <URL>`（既に origin がある場合は `git remote set-url origin <URL>`）
4. 一言伝える：「紐付けました。次に `/publish` すると GitHub にもアップロードされます。」

## ステップ0.5：新規プロジェクトのブートストラップ

以下の **いずれか** が当てはまれば「新規プロジェクト」と判断する：

- ルートに `package.json` が **存在しない**
- `PROJECT-OVERVIEW.md` に `[プロジェクト名をここに入力]` という文字列が **残っている**

両方とも当てはまらなければ、このステップはスキップしてステップ1へ進む。

### 新規プロジェクトの場合の手順 — ブレインストーミング優先

**大原則：合意できるまでファイルを書かない。** ここから先のステップ（質問・分析・提案）は完全に会話だけで進めること。`npx create-next-app` も `git commit` も `PROJECT-OVERVIEW.md` の編集も、ユーザーが「いいですね、作りましょう」と確認するまで実行しないこと。

#### ステップA：オープンに聞く

最初の質問はただひとつ：

```
準備できました。今日は何を作りますか？
アイデアがまだはっきりしていなくても大丈夫です — 一緒に考えましょう。
（じっくり考えたい場合は Shift+Tab を押すと「プランモード」に切り替えられます。
　プランモードでは、ファイルを書かずに一緒にアイデアを練れます。）
```

#### ステップB：ユーザーが迷っている場合のフォールバック

「わからない」「まだ決まってない」「アイデアがない」等の返答だったら、以下の例を出して選びやすくする：

```
例えばこんなものが作れます：

1. お客様向けのウェブサイト（会社紹介、施工事例、お問い合わせフォーム）
2. 社内で使うツール（在庫管理、顧客リスト、見積もり計算など）
3. デザインのプロトタイプ（新しい見せ方やレイアウトを試す）
4. ちょっとしたアイデアを試したい（フォーム、ギャラリー、地図など）

どれか気になるものはありますか？それとも全く別のアイデアでも大丈夫です。
```

ここでも質問は重ねないこと。ユーザーが話し出すまで待つ。

#### ステップC：黙って分析する（質問しない）

ユーザーが説明し終わったら、Claude は **頭の中だけで** 以下を決める。ユーザーには見せない：

| 項目 | 推測のしかた |
|------|-----------|
| **アプリの種類** | 顧客向け／社内ツール／プロトタイプ のどれか |
| **フレームワーク** | デフォルトは Next.js。社内ツールで認証もバックエンドも SEO も不要なら Vite。迷ったら Next.js（`CLAUDE.md` のルール参照） |
| **テーマ** | 「HARMONY」「親会社」「フォーマル」「お客様向け」のニュアンス → HARMONY ／「若い人」「カラフル」「ライフスタイル」「UNSTANDARD」 → UNSTANDARD ／ 社内ツールや手がかりなし → カスタム |
| **データベースの要否** | 下記の合図のどれかが含まれていれば「必要」、それ以外は「不要」 |
| **プロジェクト名の候補** | 説明から自然な日本語の名前を一つ考える（例：「施工事例ギャラリー」「見積もり管理ツール」） |

**データベースが必要な合図**（どれか1つでも当てはまれば「必要」）：
- ユーザーログイン／アカウント／マイページ
- データの保存・編集・一覧（お客様情報、予約、お問い合わせ履歴など）
- 投稿・コメント・写真アップロード
- 検索・絞り込み（事前に静的なデータを書いておくだけで足りるなら不要）
- 複数のユーザーが同じデータを共有する

合図がなければ **「データベース不要」**。聞かないこと。

#### ステップD：まとめて提案する

分析が終わったら、ひとつのメッセージで提案を返す。ユーザーが見るのはこのメッセージが初めて。例：

```
なるほど、こんな感じで進めようと思います：

- 「施工事例ギャラリー」というデモを作ります
- お客様向けのウェブサイトとして組み立てます
- デザインは HARMONY テーマがよさそうです（落ち着いた雰囲気で、親会社ブランドに合います）
- データベースは今回は使いません（写真とテキスト中心なので、ファイルに直接書いてしまえます）

この方向で進めてもよろしいですか？変更したい点があれば教えてください。
（例：「テーマは UNSTANDARD で」「名前は別のがいい」「お客様がログインできるようにしたい」など）
```

技術用語は出さない：
- ❌「Next.js でセットアップします」 → ✅「お客様向けのウェブサイトとして組み立てます」
- ❌「Supabase をセットアップします」 → ✅「お客様のデータを保存する仕組みを入れます」
- ❌「Vite で作ります」 → ✅「シンプルな社内ツールとして作ります」

#### ステップE：ユーザーの返答に応じてループ

- 「いいです」「OK」「進めて」「お願いします」等 → ステップF〜Hへ進む（該当する設定 → ブートストラップ実行）
- 「テーマは X で」「名前は Y で」「ログインを入れたい」等 → 提案を更新してステップDをもう一度。再確認をもらってから先へ進む
- 「やっぱり別のものを作りたい」 → ステップAに戻る

**まだファイルを書かないこと。** 「いいです」が来てから初めて、次のステップ（F・G・H）に進む。

#### ステップF：データベースが必要な場合の Supabase 確認

ステップCで「データベース必要」と判定 **かつ** ユーザーが提案に同意した場合のみ、`CLAUDE.md` の「Supabase」セクションの手順に従って Supabase のセットアップを案内する。最低限聞くこと：
- Supabase のアカウントを持っているか
- 持っていない → `supabase.com` で無料登録の手順を案内
- URL と anon key を受け取る

データベース不要なら、このステップはまるごとスキップ。

#### ステップG：カスタムテーマを選んだ場合の追加質問

ステップDで「カスタム」テーマを提案して同意された場合のみ：

質問A：「参考になるウェブサイトのリンクはありますか？」
- ある → URL を受け取って WebFetch で読む。色・フォント・トーンを `docs/DESIGN.md` の末尾に「プロジェクト固有デザイン」セクションとして追記する。
- ない → 次へ

質問B：「デザインガイド（`design.md` など）はお持ちですか？」
- ある → ファイルのパスや内容を受け取って `docs/DESIGN.md` に取り込む
- ない → `docs/DESIGN.md` の末尾に以下の TODO ブロックを追記：
  ```
  ## TODO（カスタムテーマ）
  - [ ] 主要カラーを決める
  - [ ] フォントを決める
  - [ ] 参考サイトを追加する
  ```

HARMONY や UNSTANDARD を選んだ場合はこのステップ自体をスキップ。

#### ステップH：ブートストラップの実行（ここからファイルを書く）

ユーザーが提案に同意してから初めてここに来る。順番に実行：

1. **フレームワークのセットアップ**（ステップCで決めたフレームワークに従う）：
   - **Next.js**（デフォルト・顧客向けやデータベース付き）：
     ```
     npx create-next-app@latest . --typescript --tailwind --app --no-src-dir --no-import-alias
     ```
   - **Vite**（社内ツール・認証なし・SEO 不要のみ）：
     ```
     npm create vite@latest . -- --template react-ts
     npm install
     npm install -D tailwindcss postcss autoprefixer
     npx tailwindcss init -p
     ```
   既に部分的にファイルがある場合は確認してから上書き。

2. **テーマトークンの適用**（hex 値は `docs/DESIGN.md` から取得）：
   - **HARMONY** → `tailwind.config.ts` に以下を追加：
     - `harmonyAccent: '#da2308'`（赤系オレンジ）
     - `harmonyAccentLight: '#e28174'`
     - `harmonyText: '#333333'`、`harmonyTextMuted: '#555555'`
     - `harmonyBorder: '#b3b3b3'`、`harmonyBorderLight: '#dcdcdc'`
     - `app/globals.css` で Noto Sans JP をインポート
   - **UNSTANDARD** → `tailwind.config.ts` に以下を追加：
     - `unstandardAccent: '#e9d45a'`（マスタード）
     - `unstandardAccentLight: '#f6dc30'`
     - レインボーパレット（`rainbowRed: '#ed1c24'` 等）も `docs/DESIGN.md` 参照
     - Noto Sans JP をインポート
   - **カスタム** → `create-next-app` のデフォルトのまま。`docs/DESIGN.md` の TODO に従って後で調整。

3. **PROJECT-OVERVIEW.md の初期化**：
   - **Design Theme** 行に、選んだテーマを記録（例：`HARMONY`）
   - **Summary** に、ブレインストーミングで聞き取った内容を 2〜3 文の英語で書く。何を作るのか、誰のためかを含める。例：
     > A photo gallery showcasing HARMONY's completed home projects, aimed at prospective customers browsing for design inspiration. Static content (no database) — photos and copy are edited directly in the codebase.
   - **このテーマは固定**。以降のセッションでは自動で適用される。変更したい場合は手動で編集する。

4. **コミット**：
   - `git add -A`
   - `git commit -m "プロジェクトを初期化（<プロジェクト名候補>・テーマ：<選んだテーマ>）"`

ブートストラップが終わったら、ステップ1へ進む。

## ステップ1以降：通常の起動フロー

1. 現在のブランチを確認（`git branch --show-current`）

2. **未保存の変更を確認**：`git status --short` を実行する
   - 変更がある場合 → `git stash` で一時退避してからブランチを切り替える。切り替え後に `git stash pop` で戻す。ユーザーには「作業中のファイルを一時保存しました」と日本語で伝える。
   - 変更がない場合 → そのまま次へ

3. `develop` ブランチが存在しない場合は `git checkout -b develop` で作成。存在する場合は `git checkout develop`

4. リモートが設定されている場合のみ `git pull origin develop` で最新版を取得
   - リモート未設定（フェーズ1のローカル作業）の場合はスキップ
5. `CLAUDE.md` を読んでプロジェクトのルールを確認
6. `PROJECT-OVERVIEW.md` が存在すれば読んで、プロジェクトの概要を把握
7. プロジェクト直下のファイル構造を簡単に把握（`ls` 程度でOK）
8. **日本語で締めくくる** — 状況によって伝える内容を変える：

   **ケース①：今このセッションでブートストラップを実行した直後**
   - セットアップが終わったことを伝える（例：「セットアップが終わりました。`<プロジェクト名>` の最初の画面から作っていきましょう。」）
   - 最初に作る画面・要素について自然に話を進める（例：「トップページから始めますか？それとも先に施工事例の一覧から作りますか？」）
   - 「今日は何を作りますか？」は **聞かないこと** — もう聞いたので

   **ケース②：既存プロジェクト（ブートストラップなし）**
   - 今 develop ブランチにいること
   - プロジェクトが何のためのものか（PROJECT-OVERVIEW.md の Summary から）
   - 現在のデザインテーマ（例：「HARMONY テーマで進行中です」）
   - すでに作られている主な機能・ページ
   - 「今日は何を進めますか？」と質問する

## 大切なこと

- 技術的な用語はなるべく避けてください（「ブランチ」程度はOK）
- フレンドリーに、短く、押し付けずに締めくくってください
- 新規プロジェクトのブレインストーミング中は、合意できるまで一切ファイルを書かないこと
